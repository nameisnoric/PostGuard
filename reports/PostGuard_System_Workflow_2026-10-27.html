1. ภาพรวมระบบ

PostGuard เป็น Desktop Application สำหรับประเมินท่าทางจากกล้องด้านหน้า ภาพกล้องถูกประมวลผลบนเครื่องผู้ใช้ ส่วน Backend รับผิดชอบบัญชี สิทธิ์ ข้อมูล Session, Baseline, Risk Event, Alert และ Report

2. Authentication, Privacy และข้อมูลผู้ใช้

Registration และ OTP

กรอกข้อมูล + @ku.th + Confirm Password → ส่ง OTP ผ่าน Resend
→ Verify OTP → Hash Password → สร้างบัญชี
  • ระบบรับอีเมลมหาวิทยาลัย @ku.th ตามขอบเขตโครงการ
  • Password ถูก hash ก่อนจัดเก็บ และไม่ส่งกลับไปยัง Desktop
  • Login สำเร็จได้ JWT; Desktop แนบ Bearer token กับ API ส่วนตัว
  • Forgot Password ใช้ OTP → reset token อายุจำกัด → ตั้งรหัสผ่านใหม่

Privacy Consent

ก่อนเปิด Camera Flow ระบบอ่าน consent version ปัจจุบัน หากยังไม่ยินยอมจะแสดง Privacy Notice และบันทึกเวลา/เวอร์ชันเมื่อยอมรับ Backend ตรวจซ้ำก่อนสร้าง Session เพื่อป้องกันการข้ามขั้นจาก client

Profile, Settings และ Account Lifecycle

ส่วนวิธีทำงาน

Settingsบันทึกเปิด/ปิด notification, sound, volume และ reminder interval ต่อผู้ใช้
Delete accountขอคำยืนยัน → ตั้งสถานะ PENDING_DELETION → มีช่วงกู้คืน 14 วัน → background purge ตรวจทุก 6 ชั่วโมง

Privacy by design: ภาพกล้องและภาพบัตรอ้างอิงไม่ถูกอัปโหลด Backend เก็บเฉพาะค่าตัวเลขและผลสรุปที่จำเป็น

3. Camera Flow และการแก้ภาพเอียง

1. Scan & Select → 2. Camera Adjustment
→ 3. Corrected Preview → 4. Personal Baseline

Camera Scan

  1. OpenCV ทดลองเปิด device index และอ่าน frame จริง
  2. แสดงเฉพาะกล้องที่พร้อมใช้งาน พร้อมชื่อและ resolution
  3. กล้องที่เลือกถูกลงทะเบียนด้วย device identifier เช่น opencv-index:0

Camera Adjustment ด้วยบัตรอ้างอิง

ขั้นตอนวิธี
ค้นหาบัตรGrayscale → Gaussian blur → Canny edge → dilation → contour/hull → polygon 4 มุม
ตรวจรูปทรงอัตราส่วนบัตรมาตรฐาน 85.60 × 53.98 มม., มุมใกล้ 90°, ตำแหน่งและขนาดอยู่ใน guide
ตรวจแนวคำนวณ card roll และ perspective difference; roll ต้องไม่เกิน ±5° และ perspective ไม่เกิน 10%
ความนิ่งต้องผ่าน 10 เฟรมติดต่อกัน พร้อมตัวนับ 1/10–10/10
ผลลัพธ์resolution, pixel scale X/Y/average, card roll, perspective และเวลาที่ตรวจ

Corrected Preview

หลัง Adjustment ระบบนำ card_roll_deg มาสร้าง affine rotation matrix ด้วย OpenCV แล้วใช้ warpAffine หมุนชดเชยภาพ โดยรักษาขนาด frame เดิมและใช้ border replication ลดขอบดำ

Corrected Frame = warpAffine(Raw Frame, rotation(card_roll_deg))

เฟรมหลังแก้เอียงถูกใช้ทั้ง Preview, Pose/Face Detection, Personal Baseline และ Monitoring ทำให้สิ่งที่ผู้ใช้เห็นตรงกับข้อมูลที่ระบบนำไปคำนวณ

4. Personal Baseline

Baseline คือท่านั่งปกติของผู้ใช้แต่ละคน ใช้ลดปัญหาการตัดสินทุกคนด้วยมุมคงที่เดียวกัน และผูกกับกล้อง/การตั้งกล้องครั้งนั้น
Corrected Frame → Face + Pose valid
→ เก็บ Sample → ตรวจเวลา/สัดส่วน/ความนิ่ง
→ Candidate → ผู้ใช้ยืนยัน → Save Baseline
ค่าที่เก็บการใช้งาน
Shoulder tiltระดับไหล่ซ้าย–ขวาปกติ
Neck lateral tiltการเอียงคอด้านข้างปกติ
Neck flexionค่าก้ม/เงยคออ้างอิง
Eye distance proxyบริบทระยะผู้ใช้กับกล้อง
Camera referencescale, roll, perspective, frame size และ calibrated time

การตรวจคุณภาพ

  • นับเฉพาะเฟรมที่มีข้อมูลจำเป็นครบและเป็นค่าจำนวน finite
  • ตรวจจำนวน sample, เวลาครอบคลุม, valid ratio และ stability
  • เมื่อผ่านจึงสร้าง Candidate; ผู้ใช้ต้องยืนยันก่อนบันทึก
  • Start Monitoring เปิดใช้งานหลัง Backend ตอบกลับ baseline_id สำเร็จ
การเปรียบเทียบขณะ Monitoring ใช้ผลต่างจาก Baseline ไม่ได้ใช้มุมกล้องดิบเพียงค่าเดียว จึงรองรับความแตกต่างด้านสรีระและท่านั่งเริ่มต้นได้ดีกว่า

5. Detection Pipeline

Raw Frame → Roll Correction → MediaPipe
→ Feature Validation → Posture Assessment
→ Temporal Tracking → Risk Evaluation
1
Capture: QTimer อ่านกล้องประมาณทุก 30 ms; detection ทำทุก 5 เฟรมเพื่อลดภาระ
2
MediaPipe: Pose Landmarker และ Face Landmarker สร้าง landmark บนเครื่อง
3
Context filter: ตรวจว่ามีใบหน้า/ลำตัวและบริบทเหมาะสมก่อนอนุญาตให้ประเมิน
4
Features: คำนวณ shoulder tilt, neck lateral tilt, neck flexion และ eye state/blink
5
Baseline comparison: เทียบค่าปัจจุบันกับค่าปกติส่วนบุคคลและ threshold
6
Assessment: สร้าง posture factors เฉพาะค่าที่ตรวจได้จากกล้องด้านหน้า
7
Temporal tracking: ติดตามว่า factor ต่อเนื่องกี่วินาที; data gap ไม่ถูกนับเป็นหลักฐานใหม่
8
Risk: คำนวณ RULA-adapted และส่งต่อ Risk Event Tracker

กรณีข้อมูลไม่ครบ

หาก landmark หายหรือ feature ไม่ valid ระบบส่งสถานะ NOT_EVALUATED/DATA_GAP และแสดง N/A แทนการสร้างคะแนนจากข้อมูลเดา

6. RULA-adapted Risk Score

ระบบประยุกต์แนวคิดจาก RULA เฉพาะส่วนที่กล้องด้านหน้าตรวจได้ จึงเรียกว่า RULA-adapted Front Camera ไม่ใช่ Full RULA และไม่ใช่การวินิจฉัยทางการแพทย์
หลักฐานเงื่อนไขคะแนนภายใน
Neck flexion0–10°Base 1
Neck flexion>10–20°Base 2
Neck flexion>20°Base 3
Neck extensionค่าต่ำกว่า 0°Base 4
Neck side bendingเกิน tolerance จาก baseline+1
Shoulder asymmetryเกิน tolerance จาก baseline+1
Sustained posturefactor ต่อเนื่องมากกว่า 60 วินาที+1
Internal Score = min(7, Neck Base + Side Bend + Shoulder Asymmetry + Sustained Posture)
คะแนนภายในระดับเปอร์เซ็นต์ที่แสดง
1–2LOW0–16.7%
3–4MODERATE33.3–50%
5–6HIGH66.7–83.3%
7VERY HIGH100%
Display Percentage = (Internal Score − 1) ÷ 6 × 100

Database และ Session Summary ยังเก็บคะแนน 1–7 เพื่อรักษาความหมายของ model และข้อมูลย้อนหลัง ส่วน Monitoring, Dashboard, Graph และ Report แปลงเป็น 0–100% ในชั้นแสดงผล

7. Risk Event และ Alert Policy

Risk Result → Risk Event Tracker
→ START / UPDATE / ESCALATE / RESOLVE
→ Alert Policy → Popup + Sound + Database

Risk Event Tracker

รวมเฟรมต่อเนื่องให้เป็นเหตุการณ์เดียว เพื่อลดการสร้าง Alert ทุกเฟรม รองรับสถานะ STARTED, UPDATED, ESCALATED, DEESCALATED, DATA_GAP และ RESOLVED พร้อม runtime event id

Alert Policy

การตัดสินใจเงื่อนไข
FIRSTแจ้งครั้งแรกเมื่อ event ระดับ MODERATE/HIGH ผ่าน first delay
REPEATเตือนซ้ำเมื่อพ้น cooldown; MODERATE 600 วินาที, HIGH 300 วินาที
ESCALATIONระดับสูงขึ้นสามารถข้าม cooldown
SUPPRESSEDevent ยังทำงานแต่ยังไม่ถึงเวลาที่ควรแจ้งซ้ำ

เมื่อ Policy อนุญาต Desktop แสดง popup แบบ non-modal และเล่นเสียงตาม Settings จึงไม่หยุด camera timer ผู้ใช้ยังทำงานต่อได้

การบันทึกแบบไม่บล็อก UI

  • RiskPersistenceService ใช้ worker thread เดียวเรียงลำดับคำขอ
  • lifecycle transition และ notification ถูกส่งทันที; UPDATE ปกติ throttle ทุก 5 วินาที
  • retry สูงสุด 3 ครั้ง และใช้ idempotency key ป้องกันข้อมูลซ้ำ
  • ก่อน Pause/Stop ระบบ flush งานที่ค้างเพื่อไม่ให้ event สูญหาย

8. Session Lifecycle และ Recovery

Start → RUNNING ⇄ PAUSED
Stop → COMPLETED → Summary Saved
ปิดผิดปกติ → Recovery หลัง Login → INTERRUPTED
สถานะความหมายพฤติกรรม
RUNNINGกำลังตรวจจับtimer, camera และ risk pipeline ทำงาน
PAUSEDพักชั่วคราวไม่นับช่วงพักเป็น active time และปิด active risk event
COMPLETEDผู้ใช้ Stop สำเร็จบันทึก duration, summary และ report
INTERRUPTEDsession ค้างจากการปิดผิดปกติกู้สถานะเมื่อ Login ครั้งถัดไปโดยไม่สร้าง Summary เทียม

การเปลี่ยนหน้า

เมื่อผู้ใช้ไป Dashboard หรือ History ระหว่าง RUNNING การตรวจจับยังทำงานด้วย timer เดิม ปุ่ม Monitoring จะพากลับ session เดิม ส่วน global Pause/Stop ทำงานได้จาก navigation area

การจบ Session

  1. flush Risk Event/Notification ที่รอบันทึก
  2. เรียก End Session และรับ duration จาก Backend
  3. คำนวณสถิติจาก sample ในหน่วยความจำ
  4. บันทึก Session Summary หนึ่งรายการต่อ Session
  5. หากบันทึกล้มเหลว เก็บ snapshot เพื่อ Retry และไม่เริ่ม session ใหม่ทับข้อมูล

9. Dashboard, History และ Report

Dashboard

  • จำนวน completed, active/interrupted และ active monitoring time
  • ค่าเฉลี่ยและค่าสูงสุด Risk แสดงเป็นเปอร์เซ็นต์
  • ตาราง Session ล่าสุดและจำนวน Alert ที่บันทึกจริง
  • กราฟ RULA Score Trend เรียงตามเวลา: สีน้ำเงิน = ค่าเฉลี่ย, สีแดง = ค่าสูงสุด
  • โหลด API ผ่าน Qt thread pool เพื่อไม่บล็อกการตรวจจับที่กำลังทำงาน

History และ Saved Report

History โหลด Sessions และ Summaries ที่เป็นของผู้ใช้ เลือก session เพื่อเปิดรายงานที่บันทึกไว้ รายงานอ่านค่าจากฐานข้อมูลและไม่คำนวณ detection ใหม่ จึงตรวจสอบย้อนหลังได้ตรงกับเวลาที่จบ session

Alert Events

แสดง Risk Event และ Alert Notification แยกกัน ผู้ใช้เห็นเวลาเริ่ม/จบ ระยะเวลา ระดับสูงสุด ปัจจัย และชนิดการแจ้งเตือน ทำให้ตรวจสอบได้ว่า posture risk เกิดขึ้นเมื่อใดและระบบแจ้งผู้ใช้จริงเมื่อใด

ค่า N/A มีความหมายว่าไม่มีข้อมูลที่ประเมินได้หรือยังไม่ได้เชื่อม calculation นั้น ระบบไม่แทนข้อมูลที่หายด้วยศูนย์และไม่สร้างคะแนนสมมติ

10. Data Model และ API Flow

Desktop UI → APIClient + JWT → FastAPI Router
→ Service / Validation → SQLAlchemy → PostgreSQL
Entityข้อมูลหลักความสัมพันธ์

Cameradevice id, name, resolutionUser 1:N Camera
PersonalBaselineposture reference + camera calibrationUser/Camera 1:N Baseline
Sessionstatus, start/end, pause, durationsผูก User + Camera + Baseline
RiskEventlifecycle, level, factors, durationSession 1:N RiskEvent
AlertNotificationFIRST/REPEAT/ESCALATION, emitted timeRiskEvent 1:N Notification
SessionSummaryaverage/max risk, counts, angles, blinkSession 1:1 Summary

ความถูกต้องของข้อมูล

  • Foreign key และ cascade delete รักษาความสัมพันธ์
  • Unique constraint ของ runtime event/notification ทำให้ retry ไม่สร้างแถวซ้ำ
  • Pydantic schemas ตรวจ request/response; Backend ตรวจ session ownership ซ้ำ
  • Alembic ใช้จัดลำดับ schema migration สำหรับ deployment

12. การทดสอบและข้อจำกัด

ผลทดสอบล่าสุด

ชุดทดสอบผลครอบคลุม
Desktop Unit Tests214 ผ่านทั้งหมดUI flow, camera adjustment, baseline, monitoring, risk, alert, dashboard, history
Camera correctionผ่านหมุนแก้เส้นเอียงและรักษาขนาด frame
Corrected Preview contractผ่านยืนยันว่า detector รับเฟรมหลัง adjustment

ข้อจำกัดที่ต้องสื่อสาร

  • ใช้กล้องด้านหน้าเพียงตัวเดียว จึงไม่เห็นข้อมือ แขน การบิดคอ แรง และภาระงานครบแบบ Full RULA
  • Shoulder asymmetry เป็นการประยุกต์ของ PostGuard ไม่ใช่ item อย่างเป็นทางการของ RULA
  • Risk percentage คือการแปลงเชิงเส้นเพื่อความเข้าใจง่าย ไม่ใช่ความน่าจะเป็นของการบาดเจ็บ
  • ผลลัพธ์เป็นเครื่องมือคัดกรอง/เตือนท่าทาง ไม่ใช่คำวินิจฉัยหรือคำแนะนำทางการแพทย์
  • ควรทดสอบ webcam, แสง, ระยะ, CPU และ session ระยะยาวบนเครื่องเป้าหมายก่อน release
การตีความ: คะแนนสูงหมายถึงหลักฐานท่าทางที่ระบบรองรับมีความเสี่ยงมากขึ้น ผู้ใช้ควรปรับท่าและพักตามความเหมาะสม แต่ไม่ควรใช้แทนผู้เชี่ยวชาญด้านการยศาสตร์หรือแพทย์

สรุป

PostGuard ใช้การประมวลผลภาพแบบ local ผสาน Personal Baseline, temporal evidence, RULA-adapted scoring และ event-based alerting แล้วบันทึกเฉพาะข้อมูลที่จำเป็นผ่าน Backend ที่ตรวจสิทธิ์ ทำให้ผู้ใช้ได้รับ feedback แบบ real time และตรวจสอบแนวโน้มย้อนหลังได้โดยไม่อัปโหลดภาพกล้อง
