01 — Architecture & Privacy by Design

ใช้อะไร

แยกเป็น 2 runtime: Desktop PySide6 ประมวลผลกล้องในเครื่อง และ FastAPI Backend จัดการบัญชี/ข้อมูลถาวร ผ่าน APIClient เท่านั้น

ทำอย่างไร

  • UI เรียก Desktop services; services เรียก Vision หรือ HTTP API
  • Backend router รับ request → Pydantic schema ตรวจรูปแบบ → service/model → SQLAlchemy transaction
  • Desktop ไม่ import model ฐานข้อมูล และ Backend ไม่ import Desktop UI
  • กล้องเก็บ frame ในหน่วยความจำเฉพาะรอบประมวลผล แล้วทิ้ง raw frame

ได้อะไร

ส่วนกล้องทำงานได้แม้ Backend อยู่คนละเครื่อง, ลดการส่งข้อมูลอ่อนไหว และสามารถ package Desktop แยกจาก API ได้

02 — Register, OTP, Login & JWT Refresh

ใช้อะไร

FastAPI + Pydantic, Argon2 ผ่าน pwdlib, JWT HS256, Resend email และ Desktop windows สำหรับ Register/OTP/Login

ทำอย่างไร

  1. Register ตรวจ @ku.th, password policy และ confirm password ที่ UI
  2. Backend สร้าง OTP 6 หลัก เก็บเฉพาะ OTP hash และเวลาหมดอายุ แล้วส่งผ่าน Resend
  3. เมื่อ verify สำเร็จ จึงสร้าง User และเก็บ Argon2 hash ไม่เก็บ plain password
  4. Login ตรวจ hash และสถานะบัญชี แล้วออก access token 30 นาที + refresh token 30 วัน
  5. APIClient แนบ Bearer token และเมื่อเจอ 401 จะ refresh พร้อม retry request ตาม contract
  6. auth_version ทำให้ token รุ่นเก่าถูกยกเลิกเมื่อมีการเปลี่ยนรหัสผ่าน

ได้อะไร

ผู้ใช้ KU สมัครและยืนยันอีเมลได้, login ระยะยาวโดยไม่ต้องกรอกรหัสซ้ำบ่อย และ session monitoring ที่ยาวไม่หลุดเพราะ access token หมดอายุปกติ

03 — Password Reset & Change Password

Forgot password flow

Email → POST /auth/forgot-password → OTP email OTP → POST /auth/verify-reset-otp → short-lived reset token New password → POST /auth/reset_password → invalidate used token → login again

OTP หมดอายุและใช้ซ้ำไม่ได้; reset token มี JTI สำหรับติดตามการใช้ซ้ำ และไม่ถูกเก็บใน global TokenStore

Change password flow

ผู้ใช้ที่ login อยู่กรอกรหัสเดิม + รหัสใหม่ + ยืนยัน ผ่าน dialog; Backend ตรวจรหัสเดิม, policy และห้ามใช้ค่าเดิม จากนั้นเพิ่ม auth_version และส่งอีเมลแจ้งเตือน

ได้อะไร

รองรับทั้งกรณีลืมรหัสและเปลี่ยนรหัสใน Settings พร้อมปุ่มแสดง/ซ่อนรหัสและข้อความบอกเงื่อนไขที่ผิดใน Desktop

05 — Privacy Consent

  1. ก่อนเข้า Camera Setup Desktop เรียกสถานะ consent

12 — Relative Screen Distance

หลักการ

ใช้ ratio = current_eye_distance_px / baseline_eye_distance_px เมื่อหน้าเข้าใกล้กล้อง ดวงตาในภาพจะห่างกันมากขึ้น ระบบจึงประเมินแบบ relative ไม่แปลงเป็นเซนติเมตรโดยไม่มี calibration ทางกายภาพ

State machine

NORMAL └─ ratio ≥ 1.25 ต่อเนื่อง 3s → TOO_CLOSE TOO_CLOSE └─ ratio ≤ 1.15 → NORMAL missing/invalid → NOT_EVALUATED / break continuity

ค่า enter/exit ต่างกันเพื่อ hysteresis ลดการสลับสถานะเมื่ออยู่ใกล้ threshold และ screen distance แยกจาก RULA score

ได้อะไร

แจ้งเตือนการเข้าใกล้หน้าจอเมื่อเทียบกับท่าตั้งต้นของผู้ใช้ โดยไม่อ้างว่าเป็นระยะจริงหน่วย cm

1.25, 1.15 และ 3 วินาทีเป็น configurable policy values ยังไม่ใช่ ergonomic thresholds ที่ผ่าน validation

ไฟล์หลัก: relative_screen_distance.py, screen_distance_policy.py, screen_distance_notifications.py

13 — Risk Score & Modified RULA-adapted

ทำอย่างไร

  1. เปรียบค่าปัจจุบันกับ baseline และจัด class ท่าทาง
  2. ให้คะแนนส่วนที่กล้องหน้าจับได้: คอก้ม/เงย, คอเอียงด้านข้าง, ไหล่ไม่สมดุล และท่าค้าง
  3. คะแนนภายในถูก clamp เป็น 1–7
  4. แปลงเพื่อผู้ใช้ด้วยสูตร ((score - 1) / 6) × 100 เป็น 0–100%
  5. ถ้า feature จำเป็นขาด จะคืน PARTIAL/NOT_EVALUATED แทนการสร้างคะแนนปลอม

14 — Temporal, Risk Event & Alert Lifecycle

Pipeline

Event และ Notification ต่างกัน

Alert typeความหมาย

15 — Camera Loss, Data Gap & Recovery

Data Gap คืออะไร

ช่วงที่ระบบไม่มี observation ที่ใช้ประเมินได้ เช่น กล้องหลุด, อ่าน frame ไม่สำเร็จ, ไม่เห็น pose/face หรือ context ไม่พร้อม ไม่ใช่คะแนนต่ำและไม่ควรนับเป็นท่าปกติ

ทำอย่างไร

  • CameraLossTracker จับเวลาเริ่ม/สิ้นสุด camera loss
  • Risk pipeline รับ process_data_gap() เพื่อหยุด continuity ที่ไม่มีหลักฐาน
  • Eye policy ทิ้ง rolling window ที่ไม่อาจอ้าง observation ต่อเนื่องได้
  • เมื่อกล้องกลับมา pipeline reset/recover เฉพาะ state ที่จำเป็น ไม่เอาเวลาขาดข้อมูลไปเพิ่ม risk duration
  • Session summary เก็บ data-gap metrics เพื่อบอกคุณภาพ session

ได้อะไร

ลด false alert และไม่ทำให้ duration/risk score ดูดีหรือแย่เกินจริงเพราะกล้องหาย

ไฟล์หลัก: camera_loss_tracker.py, validated_risk_pipeline_service.py, eye_alert_policy.py, migration 7c9e2a4b1d60_add_session_data_gap_metrics.py

16 — Session Lifecycle & Mini Controller

State

START → RUNNING ⇄ PAUSED → COMPLETED unexpected previous run → INTERRUPTED

ทำอย่างไร

  • Start ต้องมี consent ปัจจุบัน, camera ของ user และ baseline ที่ valid/confirmed
  • Pause เก็บ paused_at; Resume เพิ่ม paused duration และใช้ session เดิม
  • Stop ปิด event ที่เปิดอยู่, จบ session, คืนกล้อง และสร้าง summary
  • เปลี่ยนไป Dashboard/History ไม่จบ monitoring; detection controller ยังทำงาน
  • เมื่อ minimize แสดง MonitoringMiniController พร้อมภาพย่อ เวลา สถานะ Pause/Resume/Stop และ snap/hide-to-edge
  • Login รอบใหม่พบ RUNNING/PAUSED ค้าง จะให้ recovery เป็น INTERRUPTED ไม่เดา end time

ได้อะไร

ผู้ใช้ควบคุม session ได้ชัดเจนทั้งหน้าหลักและหน้าต่างเล็ก และข้อมูลไม่ถูกบันทึกเป็น completed เมื่อโปรแกรมปิดผิดปกติ
